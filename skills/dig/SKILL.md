# Dig

プラン、設計ドキュメント、会話中の実装方針について、書かれていないのに当然とされている前提を、反復インタビューで掘り起こす。目的は明確化ではなく前提への挑戦であり、ユーザーが考えていなかった論点を引き出せたら成功とする。実装や修正は行わない。

## 進め方

- 前提の分析と質問の設計は main agent が自分で行う。何が重要かの文脈を持つのは会話中の main agent だけだからである。サブエージェントに委任してよいのは、巨大な対象の事実調査だけとする
- このスキルはメイン会話で実行する。サブエージェントや fork では質問がユーザーに届かない
- 対象と、それが参照する仕様、CLAUDE.md / AGENTS.md を読み、暗黙の前提を 6 分類（実現可能性 / ユーザー / スコープ / 依存 / 期間 / アーキテクチャ）で洗い出す。各前提には、間違っていた場合の被害の大きさでリスク（high / medium / low）を付ける。明記済みの決定は質問しない
- 最もリスクの高い前提から、構造化質問ツールで聞く（無い環境では番号付きのテキスト質問にする）。1 ラウンドは 3 問まで、全体で 3 ラウンドまでとする。選んだ選択肢でプランが変わる質問だけを出す
- 1 つの糸を答えが出なくなるまで追ってから次に移る。次のラウンドでは、直前の回答が新たに露出させた前提を掘る

`/tmp/dig/<slug>.md` を台帳にし、前提マップ（前提、分類、リスク、状態）、ラウンドごとの質疑、Decisions（論点、決定、理由、残リスク）を書き足していく。

## 終了

high リスクの前提がすべて質問済み・決定・保留になったら終える。3 ラウンドに達したとき、またはユーザーに質問疲れが見えたときも終える。3 ラウンドで終える時点で未検証の high リスク前提が残っている場合だけ、もう 1 ラウンド掘るかを 1 問で確認する。

終了時のチャットには、最重要の発見（最大 3 件）、受け入れた残リスク、推奨する次のアクション、台帳のパスだけを出す。

続けて、Decisions と残リスクを GitHub Issue に日本語で書き戻す。対象に紐づく Issue があればコメントとして、無ければ新規 Issue として投稿し、URL を示す。別の PC やセッションでの作業はこの Issue から引き継ぐ。投稿の可否や投稿先が決まっていない場合だけ、1 問で確認する。投稿できない場合や不要と言われた場合は、台帳のパスを示して終える。

## 環境別の注意

- Claude Code：plan mode 中に呼ばれた場合は、ExitPlanMode の前に dig を実行し、決定をプランに反映してから提示する
- Codex：`update_plan` はチェックリスト管理用であり、決定の記録先にしない
